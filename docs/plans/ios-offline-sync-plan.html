Kaori — Offline-First iOS Plan

How to keep using the app when the laptop is offline, without breaking the vault, the LLM pipeline, or data safety.  ·  Draft v1 · for review

TL;DR — the recommendation in one paragraph

Do not reimplement the Python backend in Swift. That would mean maintaining two copies of every business rule forever — and two implementations of "what are the calories for this meal" will drift, which is the opposite of the data-safety you asked for. Instead, make iOS a local-first cache with a durable write queue (an "outbox"). The laptop stays the single brain: all real logic, all LLM, all vault sync live there, unchanged. iOS keeps a local SQLite mirror so reads are instant and offline; writes go into a local outbox + show optimistically in the UI; when the laptop is reachable the outbox flushes to the existing API and iOS pulls back the authoritative results. This is exactly the "iOS cache + Kaori backend" model you landed on at the end of your message — and it matches the three things that are already true in your system: the vault is already a one-way, hours-tolerant mirror; LLM calls are already deferred background tasks; and the iOS app is already a thin client we can extend cleanly.

The hard part is not "build a second backend." The hard part is identity & change-tracking: the DB uses auto-increment integer IDs, hard deletes, and has no "what changed since X" primitive. Most of this plan is about fixing that additively on the server so nothing existing breaks.

1 · What we're working with today

iOS app

  • SwiftUI, iOS 17+, one APIClient, Codable structs mirroring Pydantic.
  • No local DB at all. Pure thin client; data re-fetched every load.
  • Offline today = red "server unreachable" banner, writes simply fail. No queue.
  • Well-structured Store layer — a clean seam to insert a local cache.

Backend / DB

  • SQLite (WAL), ~27 tables, inline schema + idempotent ALTER migrations in database.py.
  • Auto-increment integer PKs on nearly everything (only agent_sessions is UUID).
  • Hard deletes, CASCADE. No is_deleted, no per-row change log, no device concept.
  • LLM work is already fire-and-forget async (pending → analyzing → done).

Vault coupling good news

  • One-way only: DB → markdown/CSV in the vault. No reverse flow, no conflicts.
  • Fire-and-forget; failure never breaks a write. Hours of lag is fine.
  • Only direct DB reader outside the backend: cosplay_progress.py, run on demand.
  • ⇒ Deferring writes to the laptop by hours does not break vault or skills.

API surface

  • ~60 GET reads, ~50 writes; uniform Bearer-token dependency on /api/*.
  • Partial updates already use exclude_unset — safe to merge.
  • No "changes since timestamp" endpoint and no batch write. We'll add both.
  • Some POSTs trigger irreversible LLM work — replay must be idempotent.

Both options give you offline reads and writes. The difference is purely where the authoritative logic lives. Option A keeps it in one place. Your own closing line — "it seems to become an iOS cache and the Kaori backend" — is Option A. The rest of this plan assumes A.

Note on "functionally identical backend in iOS": you get functional parity for capture and viewing (log a meal, see your feed, edit weight — all offline). You do not reimplement the derived functions (LLM analysis, AI summaries, agent chat) — those legitimately need the laptop and are designed to arrive late. That distinction is what keeps this safe and finite.

4 · The hard problems (and how each is solved)

4.1 Identity — the auto-increment problem core risk

If iOS creates a meal offline, it cannot know the server's integer id. Two devices both minting "id 41" is corruption waiting to happen. Fix: give every syncable row a stable, globally-unique identity that whoever creates it can mint locally.

  • Add sync_uuid TEXT UNIQUE (a UUID/ULID) to each syncable table. The integer id stays as the internal/FK key; sync_uuid is the cross-device identity.
  • iOS mints sync_uuid when it creates a row offline and references rows by it locally.
  • On flush, the server does an upsert keyed by sync_uuid: unknown → INSERT (assign new int id), known → UPDATE. This makes replay idempotent (a retried flush can't double-insert).
  • Server returns the sync_uuid → id mapping so iOS can resolve foreign keys for children.
Backfill: every existing row gets a sync_uuid generated once at migration time. Purely additive — existing code keeps using integer ids and never reads the new column unless it opts in.

4.2 Deletes — hard deletes are invisible to sync needs tombstones

Today a delete just removes the row. A puller has no way to learn it's gone. Add a tombstone log:

CREATE TABLE sync_deletions (
  id           INTEGER PRIMARY KEY AUTOINCREMENT,
  entity_type  TEXT NOT NULL,     -- 'meal','weight',...
  sync_uuid    TEXT NOT NULL,
  deleted_at   TEXT NOT NULL DEFAULT (datetime('now'))
);

Every delete (server- or iOS-originated) writes a tombstone. /sync/changes returns tombstones so each side can remove the row locally. CASCADE deletes emit tombstones for children too.

4.3 "What changed since X" — the missing primitive

  • Ensure every syncable table has updated_at (several already do; add to the rest) and that it bumps on every write.
  • GET /api/sync/changes?since=<cursor> returns, per entity type, rows with updated_at > cursor plus tombstones since the cursor. Cursor = a hybrid (updated_at, id) high-water mark to avoid same-timestamp gaps.

4.4 LLM / derived fields — iOS must never fabricate them already fits

Nutrition numbers, AI summaries, workout analyses, photo descriptions are computed by the laptop. Offline, iOS stores the raw capture and shows the existing pending placeholder (same UX as today's async flow). On flush, the laptop runs analysis and the values arrive on the next /sync/changes pull. No new placeholder concept is needed — it already exists.

4.5 Nested writes — workouts → exercises → sets

These must travel as one atomic operation keyed by the parent's sync_uuid, with children carrying their own sync_uuids and referencing the parent by uuid. The server resolves the whole tree in a single transaction. Same pattern for a meal + its photos.

4.6 Photos — bytes can't ride in a JSON queue

  • Offline, the photo is saved to the device and referenced by a local file URL + its sync_uuid.
  • On flush: upload bytes first (multipart, idempotent by sync_uuid), server returns the canonical /photos/… path, then the meal/post write references it.
  • The mirror swaps the local URL for the server path on the next pull. Until then the UI shows the local image — no broken thumbnails.

4.7 What does not sync as user data

CategoryTablesTreatment

4.8 Vault & external readers — unchanged

Vault sync stays entirely server-side and fires when the outbox lands. It just becomes slightly more bursty (a batch arrives at reconnect). cosplay_progress.py reads the DB on demand and is latency-tolerant. No changes required to the vault layer.

5 · Server-side changes — all additive & backward-compatible

Schema (one idempotent migration pass in database.py)

  • Add sync_uuid TEXT (UNIQUE, indexed) to each syncable table; backfill existing rows once.
  • Add updated_at where missing; ensure all writes bump it.
  • Create sync_deletions tombstone table.
  • Optional sync_origin TEXT (device id) to suppress echo / aid debugging.

Every existing endpoint keeps working untouched — the new columns are ignored by current code paths. This is the same "add column" migration style already in the repo.

Two new endpoints (a thin api/sync.py router)

POST /api/sync/push       # body: ordered list of ops, each with sync_uuid,
                          #       entity_type, op (create|update|delete), payload.
                          # Applies idempotently in a transaction per op-group;
                          # returns {sync_uuid -> id} map + per-op status + conflicts.

GET  /api/sync/changes?since=<cursor>[&types=meal,weight,...]
                          # returns upserts (rows updated_at > cursor) + tombstones,
                          # plus a new cursor high-water mark.

Internally these call the existing services (so nutrition triggers, vault sync, LLM tasks all fire exactly as they do for the live API). The sync layer is glue, not new business logic.

Because the Store layer already centralizes data access, Views barely change — they keep observing the same stores.

7 · Conflict policy (single user ⇒ simple)

  • Inserts (the common offline case — new meals/weights) never conflict; they're new sync_uuids.
  • Edits to the same row on both sides (rare for one person): last-write-wins by updated_at, but the server never accepts a stale overwrite (if server's updated_at > incoming base, mark the op conflict and let iOS re-pull + re-apply on top). The raw/analysis/override audit trail means we lose nothing irrecoverable.
  • Delete vs edit: delete wins (tombstone), edit dropped — surfaced to the user, not silent.

9 · Data-safety guarantees baked in

  • Laptop DB is canonical — iOS proposes, the server disposes. iOS never writes authoritative/derived values.
  • Idempotent replay via sync_uuid upserts — a retried flush can't duplicate.
  • Additive migrations — Phase 0 is reversible; existing endpoints/vault untouched.
  • Test mode — the existing POST /api/test-mode/fork lets us build and validate the entire sync layer against a forked DB before touching real data.
  • No silent loss — conflicts and dropped edits are surfaced; the analysis/override audit trail preserves history.
  • Vault is downstream & one-way — worst case it's hours stale, which it already tolerates.

10 · Non-goals (explicitly out of scope)

  • Running Python or any LLM on the phone. (Not possible / not desired.)
  • Offline agent chat turns, offline AI summaries, offline meal analysis numbers — these are deferred, not replicated.
  • Multi-user / true concurrent-editor CRDT machinery — overkill for one person on two devices.
  • A second authoritative implementation of business logic in Swift.

11 · Battery & resource budget net lighter than today

Offline capability must not cost battery. Done right, Option A is cheaper than the current app, because reads stop hitting the network.

  • Reads are local. Today every screen load round-trips to the laptop and wakes the radio. With the mirror, feed/meals/etc. read from on-device SQLite — no radio, no network. This removes most of the app's current battery cost.
  • No polling. We never run a timer asking "is the laptop up?". Reachability comes from the OS's free NWPathMonitor callback — iOS already tracks the network and hands us the event.
  • No retry storms. While the laptop is unreachable the outbox just sits in SQLite costing nothing. No background retries hammering the radio; we don't attempt a flush until the OS reports network is back.
  • No persistent socket / no push connection to the laptop.
  • Sync runs only on cheap triggers: (1) app foreground, (2) a user write while online, (3) an OS-granted BGTaskScheduler refresh — which iOS only schedules when it's already cheap (typically Wi-Fi and/or charging). The app already has this plumbing in BackgroundTaskManager.
  • Reconnect = one short burst (flush queue once, pull changes once), bounded and brief, happening when you're back on a network anyway.
Principle: passive reachability + opportunistic, OS-budgeted sync + a queue that costs nothing while it waits. No timers, no polling, no open sockets, no foreground network for reads.
